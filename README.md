# 想让 AI 真正懂业务，RAG 这几步不能省

企业里最容易被低估的一类 AI 问题，往往问得很简单。

“上海出差住酒店能报多少？”

这句话交给通用大模型，它可以写出一段看起来很像答案的内容。可企业真正需要它先做几件事，找到当前有效的差旅制度，确认提问者的职级和出差城市，再把条款解释成能执行的步骤。

任何一步拿错，后面的回答写得再流畅也没用。

大模型进入企业以后，很多团队最先发现的就是这个问题。模型知道公共知识，却不知道公司的报销制度、产品版本、客户历史、合同条款和项目进展。更麻烦的是，这些资料一直在更新，还有不同的权限边界。

![](assets/01.png)

RAG 出现得很及时。

它的全称是 Retrieval Augmented Generation，也就是检索增强生成。用户提问以后，系统先去企业自己的资料里找相关内容，再把找到的内容和问题一起交给大模型。模型据此组织答案，并把来源带回来。

这件事听上去像“给 AI 接一个知识库”，实际做起来，牵动的是企业怎么整理资料、怎么确认版本、怎么管理权限，以及怎么让员工相信 AI 给出的答案。

![](assets/02.png)

## 企业缺的不是文档，缺的是能被问出来的知识

大多数公司并不缺资料。

制度在网盘里，产品手册在 Wiki 里，客户会议纪要散在不同群聊，售后案例躺在工单系统，销售有自己的案例库，研发还有一套内部文档。有人问问题时，往往知道答案大概在哪，却要花十几分钟翻文件、问同事、确认版本。

这类工作看上去不复杂，实际消耗了大量碎片时间。

RAG 的第一层价值，就是把这些资料变成可以直接提问的对象。员工不必记住制度文件叫什么，也不用知道它在哪个文件夹。系统根据问题去找资料，把关键段落拿回来，再把原文链接交给用户。

这种体验对新员工尤其明显。

刚入职的人最常问的并不是多么复杂的问题，而是权限怎么申请、设备怎么领、客户资料能不能导出、某项费用怎么报。过去，这些问题会不断流向行政、财务、IT 和直属主管。接入 RAG 之后，很多问题可以先由 AI 给出制度依据和办理路径，员工再按链接核对。

它没有替代负责制度的人，却把重复解释这件事做得更顺。

AWS 在 RAG 的技术说明里，把它定义为让模型在回答前参考企业内部文档等外部数据的一种方式。企业不需要每次更新制度就重新训练模型，可以让模型在问答时查阅最新资料。

这也是 RAG 会成为企业 AI 第一站的原因。它先解决的是信息怎么被可靠地调用，后面的 Agent、自动化和复杂流程，才有稳定的基础。

## RAG 到底怎样工作

可以把它理解成一次有准备的回答。

企业先把文档接进系统。合同、制度、产品资料、FAQ、工单记录，经过清洗和解析后，被拆成许多可以独立理解的小段。每一段除了正文，还会带上标题、发布日期、部门、版本、原文链接和权限等信息。

用户提问时，系统会先理解问题，再从这些内容里找相关段落。

比如用户问“上海出差住酒店能报多少”，系统不该只看“酒店”这个词。它还需要识别出问题与差旅制度有关，优先找最新版本，筛选适用于上海和用户职级的内容。检索结果进入大模型后，模型把条款整理成一段人能看懂的话。

最后，用户看到的不该只是一句金额。

更好的回答会告诉他适用条件、对应条款、需要提交什么材料，并附上制度原文。这样，AI 的答案成了一个入口，用户仍能回到证据本身。

这套流程里，大模型负责理解和表达，检索系统负责找资料，企业资料本身负责提供依据。三件事缺一件，体验都会掉下来。

## RAG 最容易在哪儿出问题

很多团队做 RAG，第一反应是选模型、选向量数据库。项目往下走一段，才发现最难的地方在资料本身。

一份制度文档通常很长。里面有适用范围、例外条款、金额标准、流程说明和附件。系统如果按固定字数硬切，很容易把“住宿上限”切到前一段，把“适用城市和职级”切到后一段。用户问一个金额，AI 找到前一段，看起来有理有据，实际少了最关键的限制。

文档切分因此是一件很细的工作。

有些资料适合按章节切，有些要按问答对切，有表格的制度需要保留表头和字段关系，扫描件还要先处理 OCR。微软在 RAG 文档里特别提醒，过大的文本块会增加成本、占用模型上下文，也容易把无关信息一起带进回答。

切分完成以后，检索又是第二道关。

用户的问法和制度里的写法经常不同。用户问“报销上限”，文档可能写“住宿标准”。用户问“能不能带走客户资料”，文件里可能叫“数据导出管理规范”。单靠关键词，容易漏掉同义表达。只依赖向量检索，又可能找回语义接近、却不适用于当前情况的内容。

成熟一点的 RAG 系统，通常会把关键词检索、向量检索、时间筛选、权限筛选和重排序放在一起用。

关键词帮系统抓住准确名词和编号。向量检索负责理解不同说法。时间和版本筛掉旧资料。权限决定用户能不能看到这份内容。重排序再从一批候选资料里挑出最值得交给模型的几段。

这一层做得好，AI 才能少说废话。

还有一个容易被忽略的问题，RAG 也会答错。

检索结果不完整，文档本身互相冲突，用户的问题超出资料覆盖范围，模型都有可能补出一段很像答案的话。产品需要给它留出收住的能力。

资料不够时，回答“当前知识库里没有找到明确规定”。发现制度版本冲突时，提示用户确认最新版本。涉及金额、合规、客户承诺和安全事项时，默认展示出处和生效日期。

企业用户愿意用 AI，很大程度上取决于它能否把“不确定”说清楚。

## RAG 已经在哪些地方先跑起来了

RAG 最适合的场景，通常有几个共同点。

资料多，更新快，问题重复，回答还需要有依据。

员工问答是最常见的一类。公司制度、流程、工具手册和项目规范接入以后，员工可以直接问“这项权限怎么申请”“客户信息能不能导出”“设备报修找谁”。系统给出步骤和原文入口，行政、HR、IT 团队也能从重复答疑里腾出时间。

客服和售后是另一类。

客服每天面对产品版本、故障排查、服务边界和历史工单。RAG 可以先从有效的产品手册、公告和案例中找答案，再让人工客服确认后发送。NVIDIA 在企业 RAG 部署指南里，把 IT 支持、客户服务和工程代码分析列为典型场景。它们的共同点是资料繁杂，用户又希望得到具体、及时、能执行的答复。

销售和解决方案团队也很适合做 RAG。

销售准备客户拜访前，需要翻客户历史沟通、行业案例、产品能力和报价边界。过去这些内容散在 CRM、文档库和同事手里。RAG 可以帮助他先把资料找全，让准备工作更快一些。

不过，这类场景必须先解决权限。

销售能看到自己负责客户的历史，不能因为一句自然语言提问，就检索到别的团队的合同和报价。RAG 把资料变得更容易被问到，也把原来藏在系统深处的权限问题摆到了台面上。

## AI 产品经理做 RAG，先把这几件事想明白

RAG 真正进入业务后，产品经理最容易犯的错误，是把它当成一个“接入知识库就能回答问题”的功能。用户在意的从来不是系统里存了多少份文档，而是关键时刻能不能给出可信、可用、符合权限的答案。

第一，别一开始就追求“大而全”，先选一个高频、结果可验证的场景。

比如员工制度问答、客服知识查询、销售方案准备。这些场景的共同点是，用户原本就要花时间翻资料，答案也大多能在现有文档中找到。先把一个场景跑通，观察用户到底问了什么、系统漏掉了什么，再决定要不要扩展到更多部门。

第二，知识库上线前，先把文档治理做一遍。

过期资料、重复版本、没有明确归属的文件，都会把错误带进回答里。每份进入知识库的内容，最好都能标记来源、负责人、生效时间、适用范围和权限级别。这样用户追问“这条规定从哪里来的”，系统才能给出明确依据，运营人员也知道该找谁更新。

第三，把“找不到答案”设计成一个正常结果。

RAG 的价值不在于每次都要回答。检索到的材料相关性不够、资料已经过期、用户没有查看权限时，系统应该坦诚说明，并给出下一步动作，比如推荐相关制度入口、提示联系业务负责人，或邀请用户补充问题。比起一本正经地生成错误答案，这种克制更容易建立信任。

第四，给答案保留出处，让用户能核验。

在企业场景里，一段回答往往会影响客服口径、报价内容、制度执行甚至风险判断。产品上应当让用户看到答案引用了哪些文件、具体来自哪一段、文件是什么版本。引用不只是一个展示功能，它还是用户纠错、运营排查和持续优化的入口。

第五，把用户反馈接进知识运营闭环。

用户点了“没帮助”，不代表模型一定答错了。可能是没检索到正确文档，可能是切分方式不合理，也可能是资料本身没有覆盖这个问题。产品团队要把这些反馈按问题类型沉淀下来，定期回看高频未命中问题、低满意度答案和重复追问，推动文档补齐、检索优化与权限调整。

RAG 做到后面，拼的并不是谁接入的大模型更多，而是谁更愿意把知识、流程和用户反馈耐心地整理好。模型负责理解与生成，产品要负责让它在该说话的时候说得有据可查，在不该回答的时候知道停下来。

## 写在最后

企业落地 AI，很多时候要从一次朴素的提问开始。

AI 能不能在用户需要的时候，找到当前有效、用户有权查看、又足以支持答案的那几段资料。

这件事做好了，知识库才会从一堆存放文件的地方，变成能参与工作的人。
